# Cardenveil release notes

Patch notes for a tabletop plugin played by a **GM and their players** in Owlbear Rodeo. Not a changelog for developers: the developer record is `git log`, `AGENTS.md` and the `docs/documentation/` space.

The question every line must answer for the reader: *does this change something at my table, and what do I do about it?*

## Where a note lives

`docs/changelog/<version>.md`, full semver (`2.7.4.md`, never `2.7.md`).

Consecutive releases that only patch the same subsystem are **fused** into one page,
`<first>-<last>.md` (e.g. `2.7.1-2.7.15.md`), with each bullet carrying the version it
landed in, in italics at the end: `- **La barre a un fond** _(2.7.2)_ : …`. A run of
releases describing the same popover twice is one page, not fifteen.

`SUMMARY.md` is regenerated by GitBook on export — never hand-edit its labels or grouping.

Naming, title format and the audience contract are in the repo's `AGENTS.md` (`### Changelog`). Follow them; this file covers the body.

## Note structure

```markdown
# Cardenveil <version> — <résumé>

## 🚀 Nouveau
- **<accroche courte>** : <ce que le joueur voit, et où le trouver>.

## ✨ Amélioré
- **<accroche>** : <ce qui est mieux, concrètement>.

## 🐛 Corrigé
- **<symptôme que le joueur reconnaîtra>** : <comportement correct maintenant>.

## À faire une fois après la mise à jour
- <action concrète : recharger la table, re-sélectionner un jeton…>
```

Category sections appear in this fixed order, and **only when non-empty**:

| Section | Icon | Use for |
|---|---|---|
| Nouveau | 🚀 | A capability that did not exist |
| Amélioré | ✨ | Something existing that got better |
| Performance | ⚡ | Measurably faster, smaller, smoother — say the number |
| Corrigé | 🐛 | A defect the table could hit |
| Changement | ⚠️ | Behaviour now differs; the reader must adapt |
| Sécurité | 🔒 | Identity, permissions, data exposure |

`À faire une fois après la mise à jour` goes last and exists only when the table must act. If nothing must be done, omit it — do not write "aucune action".

Most releases use 🚀 / ✨ / 🐛 only. A tiny fix release is one 🐛 section, and that is a complete note.

## Writing the body

One bullet per change. Lead with a bold phrase naming the thing in the player's vocabulary ("le popover de main", "la fiche", "le panneau 🎟 Tokens"), then a colon, then the consequence. One sentence, optionally one more if the reader needs to know where to look.

Say where to find it. "Un bouton **Réinitialiser** apparaît dans l'en-tête" beats "la fonction de réinitialisation a été ajoutée".

Say what it replaces when the change is visible. "L'éventail fait maintenant 164 px (380 avant)" tells the reader more than "taille optimisée".

Name the symptom, not the cause, for fixes. The reader has never seen a stack trace.

## Translate, or leave it out

| The commit says | The note says |
|---|---|
| `anchorReference` manquant | Le popover revient à la bonne position |
| `setWidth`/`setHeight` n'atteignent pas l'iframe | L'éventail ne se coupe plus en bas |
| Le compteur de tentatives se remettait à zéro | Plus besoin de recharger après une coupure |
| `BroadcastChannel` réintroduit | *Rien — aucun effet visible* |
| `SET_RACE` valide contre `RACE_IDS` | *Rien — détail serveur* |

**Never in a patch note:** file paths, function or variable names, SQL, RPC names, action-type names (`SET_RACE`, `SYNC_TOKENS`), table or column names, test counts, dependency bumps, framework names, commit hashes.

**Exclude entirely:** refactors, renames, internal reorganisations, test-only work, tooling, docs-only edits to developer pages. If a release only contains those, it does not get a note.

**Include:** anything visible in the hand popover, the sheet, the GM dashboard, dice, tokens, cards, races, capacities, imports — and every fix a player reported.

## Where the input comes from

1. `git log --oneline <previous-version>..HEAD` for the change set. `git describe`/`src/version.js` for the version.
2. Read the commits, not just their subjects — several small commits often combine into one player-facing sentence.
3. When a change is already documented in `docs/documentation/`, use that page's vocabulary so the note and the docs agree.
4. Group by what the player experiences, not by commit. Five commits fixing the same popover are one bullet.

## Voice

French, second person plural or impersonal ("vous pouvez", "le popover revient"), present tense. Player vocabulary: main, éventail, fiche, jetons, défausser, cristalliser. Never "l'utilisateur", never marketing superlatives, never "nous sommes ravis".

Match the tone of the surrounding notes: a competent friend who ran the table with you and is telling you what changed.

## Before publishing

- [ ] Title matches `# Cardenveil <version> — <résumé>`, résumé lowercase, 3–8 words.
- [ ] No code identifiers, paths, or test counts anywhere in the body.
- [ ] Every bullet is something a player or GM can see or do.
- [ ] Category order respected; no empty sections.
- [ ] `À faire une fois après la mise à jour` present only if action is needed.
- [ ] Version in the filename and title agree with `src/version.js`.

## Rewriting an existing note

Strip the developer detail, regroup the material into the categories above, and keep every player-visible fact. Do not drop a fix because it is small, and do not keep a paragraph because it is well written — a note is a list of what changed, not an essay. The tests for a good rewrite: nothing technical survives, no fact is lost, and a player can skim it in thirty seconds.
